# Xila: a modular embedded operating system in Rust

## The problem

Microcontrollers impose tight memory, storage and CPU budgets, and most firmware ends up as a single program built for one board. I wanted the comforts of a modular system on these devices: separate drivers, a filesystem, tasks, a graphical interface and applications that are not compiled into the system image.

The core of the work is therefore to **define reusable contracts** between system services, hardware and programs, rather than to target one board.

## Architecture

<ArchitectureFlow title="Main layers of Xila" steps={[{ title: 'Drivers', detail: 'Native Linux, browser and hardware targets, assembled in the Platforms repository.' }, { title: 'Subsystems', detail: 'Tasks, VFS, networking, graphics, memory and time, written in Rust.' }, { title: 'Execution boundary', detail: 'Wasmi runtime and guest/host bindings.' }, { title: 'Applications', detail: 'WebAssembly guests such as Calculator and Weather, plus the graphical shell.' }]} />

The code is split across three repositories. **Core** holds the portable crates, **Applications** the official programs and the Wasmi runtime, and **Platforms** the concrete drivers and the final assembly for each target. Every crate has one of four roles: a **subsystem** owns a runtime service, a **library** defines contracts or implementations, a **driver** adapts a capability to a platform, and an **executable** is a program that uses the assembled services.

A file request from a program goes through the VFS, then the filesystem contracts, before reaching a mounted LittleFS instance or a device driver. A WebAssembly guest takes the same path through the runtime bindings: it reaches the same subsystem managers as native programs.

## Technical choices

- **Rust system, WebAssembly applications.** The services are written in Rust; applications are separate Wasm binaries run by the **Wasmi** interpreter, behind an explicit execution boundary.
- **Cooperative scheduling with fuel.** Guest execution consumes fuel; when it runs out, or when the guest yields, control returns to the executor. Functions are translated before execution so that a pause never interrupts a translation, at the cost of more startup work.
- **Shared interface theme.** The graphical layer uses **LVGL** with [lvgl_theme_shadcn](/projects/lvgl-theme-shadcn), a theme I also maintain as a separate library.
- **Languages built into the binary.** Each language is embedded at compile time, with English as the fallback and catalogs for French, Spanish, German, Brazilian Portuguese, Italian and Polish.
- **Develop on Linux and in the browser first.** The native target makes it easier to inspect CPU and memory use before testing shared code on an embedded board.

## Results

Xila is open source under the Apache 2.0 license and documented on [xila.dev](https://www.xila.dev/docs/), with tutorials and a component map. The browser demo runs the system compiled to WebAssembly, with separate WASI applications: Calculator, Clock, Pixel Painter, Text Editor, Synth and Weather. It stores its disk in the browser through OPFS.

## Limitations

Xila is under active development, and hardware support varies by target. The native and browser examples are development environments: they do not prove that a given board is supported, and checks run on the Linux host do not prove that the code is correct on ESP32, nRF or STM32 hardware. The Wasm interpreter, the abstraction layers and LVGL all cost memory and CPU time, which has to be measured on the target device.
